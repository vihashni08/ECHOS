# Why four agents, and how many run per case

Generated by `scripts/tuning/team_design.py` from `reports/metrics/team_design.json`. Not a diagnostic claim; a design argument plus replayed counts.

## Rule: when does a part deserve its own agent?

A component is an agent only if it differs from every other agent in **(a) goal, (b) authority / tools, (c) timing and failure profile**. Checked against the registry: every agent has a `never` clause = True; goal, authority and timing are pairwise different = True.

| Agent | (a) Goal | (b) Authority / tools | (c) Timing and failure |
|---|---|---|---|
| triage | one status per patient-day | reads detector outputs; writes status and opens the case; the ONLY part that decides | synchronous, on the alert path; rules, cannot hang |
| investigator | explain WHY the status was given | bounded tool loop over the person's own history (<= 7 checks); writes the case file; cannot change the status | after the alert is queued; may fail without losing anything |
| coordinator | make sure someone acts on an alert | owns the alert lifecycle, wall-clock timers, second contact, care tasks; cannot suppress the first alert | long-running; days, not milliseconds; state survives a restart |
| report | say it in plain words for people | LLM + retrieval tools + non-LLM validator; writes text only | slow, rate-limited, can be down; template fallback |

Detectors are not counted: they sense and never decide, and they are always on. The Team Planner is the coordination layer, not a fifth agent.

## Alternatives considered

Criteria are properties of the design (arguments by construction). Only the 4-agent design was built and measured; **no monolith or 2-agent version was implemented**, so there is no measured head-to-head.

| Design | Agents | alert path independent of slow work | decider is not the writer | a slow part cannot stop a fast part | timers (ack / escalation) kept apart from per-day work |
|---|---|---|---|---|---|
| 1 agent (monolith): one loop: score, decide, investigate, write, chase acknowledgements | 1 | no: the alert waits behind whatever the loop is doing (an LLM call, a retry) | no | no | no |
| 2 agents (decide + write): Triage; Report (investigation and alert follow-up folded into one of them) | 2 | yes | yes | yes | no: a day-long acknowledgement timer sits inside a per-day writer |
| 4 agents (ECHOS): Triage; Case Investigator; Care Coordinator; Report | 4 | yes | yes | yes | yes |
| 6 agents: as 4, plus a separate Validator agent and a separate Escalation agent | 6 | yes | yes | yes | yes |

Why not six: the validator is plain code that has to run in the same call as the writer (one retry on a failed check), and escalation needs the Coordinator's own alert state, so splitting either adds a hand-over and a second place where state can go out of step, without a different goal or authority.

## Evidence that the split costs the alert path nothing (existing measurements)

- Alert queued a median 1.3 ms after the event; sent (dry-run mailer, no load) p95 33 ms (`alert_latency.json`; says nothing about real SMTP).
- Killing the `fall` worker mid-run: 0 lost alerts, falls alerted 9/9 (`kill_test.json`).
- Switching the report gate on left triage identical = True, alerts identical = True, alerts missed = 0 (`gate_eval.json`).

## What the Team Planner changes at run time

The planner (`echos/team/planner.py`) was replayed on the 1265 replayed patient-days (20 patients, out-of-fold scores).

| Status | Days | Agents on the case |
|---|---|---|
| NORMAL | 940 | 2 of 4 |
| MONITOR | 270 | 4 of 4 |
| URGENT | 55 | 4 of 4 |

- Mean team size 2.514 of 4. Agent runs: 3180 vs 5060 if all four always ran (1880 avoided, 37.2%).
- Report LLM request ceiling: 1625 vs 6325 if every day could use the LLM (ceilings, not measured usage).
- Without scores (cutoff not applied) the Investigator runs on exactly the non-Normal days = True; near-miss watch days are counted in the routing section below.

## The routing algorithm (Triage stage 2)

Triage has two stages. Stage 1 (`echos/orchestrator/triage.py`) turns detector outputs into a status with if-then rules. Stage 2 (`echos/team/planner.py`) decides which agents the case needs, with one ratio and one cutoff. It is an algorithm, not a trained model: nothing labels "the right agents", so a learned selector could not be validated.

**Step 1: nearest-threshold ratio.** Each detector k (vitals, fall) gives a score p_k and has its own alert threshold tau_k (config `triage`). How close the case is to an alert is the largest ratio:

```
r = max_k ( p_k / tau_k )          r = 1: exactly at an alert threshold;  r = 0.5: half way
```

A fixed vitals rule that fired while monitoring was degraded counts as r = 1. r is a routing score, not a probability.

**Step 2: routing rule.**

```
rule fired (MONITOR / URGENT)       -> Investigator + Care Coordinator          (hard evidence, no cutoff)
no rule fired and  r > theta         -> Investigator writes a short WATCH file   (near miss; nobody else is called)
otherwise                            -> Triage + template report only
URGENT                               -> the Coordinator owns the alert, whatever theta is
```

The URGENT line does not depend on theta (tested for theta = 0, 1 and 10^9), so no setting of the cutoff can remove the alert owner. It never changes the status or delays an alert.

**Step 3: the cutoff comes from a call budget.** On every replayed day where no rule fired (status Normal, the near-miss days) a watch call is a *false call*. theta is the smallest value for which false calls stay within a budget B per patient-week (patient-weeks = all patient-days / 7, as `scripts/tuning/choose_monitor_thresholds.py`), that is the (1 - B x patient-weeks / Normal days) quantile of r on the Normal days (strict `>`, ties are not called):

```
theta = min { t : #(Normal days with r > t) <= B * patient_weeks }
```

theta is in plain units: theta = 0.8181 means "watch a day when any detector is above 82% of its own alert threshold". Budget grid (1265 patient-days, 20 patients, 940 Normal days; default B = 0.25; `scripts/tuning/choose_routing_threshold.py`, `reports/metrics/routing_thresholds.json`):

| B (false calls / patient-week) | allowed calls | theta | achieved / patient-week | labelled days among called |
|---|---|---|---|---|
| 0.1 | 18 | 0.9003 | 0.1 | 5 of 18 |
| 0.25 (default) | 45 | 0.8181 | 0.249 | 15 of 45 |
| 0.5 | 90 | 0.6593 | 0.498 | 27 of 90 |
| 1.0 | 180 | 0.4887 | 0.996 | 31 of 180 |

Patient bootstrap (1000 resamples of 20 patients, seed from config): theta 95% interval 0.6978 to 0.8574; with about 20 patients treat even this as rough. Cross-check, not the choice: the last column counts days with a clinical event label (Labels.csv, provenance unverified) among the called Normal days; it is a weak sensitivity check and supports no claim that near-miss days are more often clinically relevant.

**Replay evidence** (`scripts/evaluation/routing_eval.py`, 1265 patient-days, stored out-of-fold detector scores):

- Parity: with the cutoff switched off the routing equals the previous status-based routing on 1265 of 1265 days.
- With theta = 0.8181 45 Normal days change: they are the near-miss watch days (0.249 per patient-week, the budget). They add the Investigator only ({'investigator': 45}); the Coordinator is called on 0 of them. Each writes a short watch file (no alert, template report, not counted towards a clinician review).
- On the 940 Normal days r has median 0.209, 90th percentile 0.653, 99th percentile 0.95, maximum 0.994.
- Safety floor: all 55 Urgent days have the Investigator and the Coordinator as owner for every tested theta = {'0.0': True, '1.0': True, '1000000000.0': True}.

Sensitivity to the cutoff:

| theta | watch days | per patient-week | mean team size |
|---|---|---|---|
| 0.5 | 174 | 0.963 | 2.651 |
| 0.6 | 120 | 0.664 | 2.609 |
| 0.7 | 74 | 0.409 | 2.572 |
| 0.8 | 52 | 0.288 | 2.555 |
| 0.9 | 19 | 0.105 | 2.529 |
| 1.0 | 0 | 0.0 | 2.514 |

The budget is a stated preference (how many near-miss watch files per patient-week are acceptable), not an estimate of harm. The earlier version used a cost-based Bayes gate whose hand-set loss was not derived; it was removed because it reduced to the same status-based rule.

## Limits

- The routing is an algorithm with a budget-chosen cutoff, not a learned allocation. Its counts follow from the status mix, so the saving is large only because most days are Normal.
- Replayed days come from out-of-fold scores of 20 patients over three months: wide uncertainty, not a deployment estimate.
- The 'urgent type' per replayed day is inferred from the reason text; it only affects the wording of the reason, not the team size.
- A real ablation (build the monolith, compare alert latency and report quality) was not done.
